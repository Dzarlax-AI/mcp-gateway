Ротация ключа шифрования gateway и пароля БД

Редакция 1 · Согласована пользователем · Локальная реализация и репетиция завершены. Production-ротация не выполнялась.

1. Цель и границы

Заменить засвеченные AES-256-GCM ключ gateway и пароль роли PostgreSQL mcp_gateway_runtime. Сохранить точные upstream-credentials, подключения, клиентские токены и хэши, права, switch-состояния, batch-профили и endpoint bindings. Старый пароль перестаёт принимать новые подключения; старый ключ перестаёт расшифровывать действующие ciphertext.

Короткая остановка только gateway обязательна: SQL и файловая конфигурация не переключаются одной общей транзакцией. Продолжительность определим по репетиции; обещание zero downtime не даём. PostgreSQL, Traefik, Authentik и календарный сервис не перезапускаются. Работа inline, без subagents: единая операция над связанными DB/env/recovery состояниями.

Не входят: ротация upstream-токенов или клиентских ключей, создание/удаление principals, SQL migration, изменение прав роли, TLS/сети, исправление HA AJAX и календарные/device mutations. Изменения upstream/client токенов потребуются отдельно, если выяснится, что злоумышленник получил ciphertext или backup; простое перешифрование не отзывает уже украденный plaintext.

3. Инварианты и обращение с секретами

  • Registry document сохраняется побайтно, revision увеличивается ровно на1 при успешном перешифровании. Schema, row IDs/counts, role privileges и client digest/metadata не меняются. Сравнение plaintext до/после выполняется в памяти; наружу только boolean/count. Никаких plaintext-хэшей upstream-секретов в evidence.
  • Все записи обеих таблиц проверяются старым ключом до записи. Одна повреждённая, чужая AAD, digest mismatch, отсутствующая/лишняя запись или сменившаяся revision → отказ всей транзакции. Новые ciphertext получают новые cryptographic random nonces и сохраняют прежнюю AAD/формат, включая длину client ciphertext75.
  • Новые AES key и DB password генерируются на VPS криптографическим RNG. Не проходят через чат, clipboard, shell substitutions, argv, SQL command line, CI secrets/artifacts или локальные исходники. Вызовы содержат только пути и безопасные флаги. Privileged operator читает mode0600 файлы; umask077; исключение symlink и небезопасных permissions.
  • Не использовать subprocess check=True там, где argv/env может содержать секреты. Запретить panic/raw exception/raw stderr, shell xtrace, DEBUG и dump effective Compose/env. Верхний уровень выдаёт только фиксированный код этапа и безопасный status. Тесты проверяют stdout/stderr, failed commands и rollback paths на утечки.
  • Перед сменой пароля проверить PostgreSQL statement/error/duration/audit logging. Выбрать протестированный механизм клиентского SCRAM verifier, совместимый с psql \password; plaintext не помещается в SQL. Verifier тоже private. Никакого глобального отключения logging; локальную защиту password-operation согласовать в конкретной реализации и проверить synthetic logs.

Основание для client-side password encryption: PostgreSQL17 ALTER ROLE предупреждает о plaintext в истории/логах и рекомендует \password; SCRAM password authentication. Защита новых секретов не меняет текущую транспортную конфигурацию.

4. Подготовка и локальная репетиция

  1. Добавить новый explicit registry rotate-secret-key (предлагаемый контракт): expected revision + old/new key file paths, verify-only и commit modes. Не auto-run при startup. Новый store метод блокирует registry row и обе encrypted-таблицы на период одной транзакции, валидирует полную пару Config/secrets и client digests, меняет только ciphertext и revision. Без orphan cleanup и без повторного применения after ambiguous commit.
  2. Добавить operator orchestration script с fixed stage codes, owner-only journal и безопасной заменой env через temp file + fsync + rename. Journal хранит phase/revision; секреты отдельно. Метод смены собственного DB password и re-encryption под одной PostgreSQL транзакцией предпочтителен, но принимается только после репетиции PG17. Если атомарное объединение невозможно выбранным API, использовать два явных этапа и проверяемое recovery-состояние между ними; не приступать к production до фиксации этого решения и обновления плана.
  3. SQLite + disposable PostgreSQL synthetic fixtures:2upstreams, env-principal, hash-only managed key и recoverable managed key. Проверить authentication теми же токенами, повторный reveal без вывода, сохранность header/metadata/permissions. Производственные секреты локально не переносить.
  4. Прогнать wrong key, corrupted final row, stale revision, concurrent writer, disk/rename failure, termination до/после SQL commit и до/после env replace, неизвестный исход commit, повторный запуск. Проверить новое соединение новым паролем, отказ старому и restart с новым ключом. Dry-run не пишет в DB/env/role.
  5. Тесты: focused store/CLI/orchestrator tests, go test -race ./..., go vet ./..., build. Отдельный disposable PG CI check. После review diff и отдельного commit/push разрешения — GitHub Actions image. Не использовать locally built release image для production. Новая CLI включается в CI image; существующий runtime без автоматической ротации.

Вероятные файлы: existing cmd/registry/main.go, internal/store/store.go/client_keys.go; new internal/store/rotation.go, focused tests, scripts/rotate_gateway_secrets.py, docs/deployment/secret-rotation.md, CI workflow и image overlay. Точные интерфейсы и commit ordering принимаются по репетиции.

Fresh baseline: registry/schema, exact document bytes и role grants, encryption references/counts, client token digests в protected comparison data, все контейнеры; проверка admin и текущего public client. Разрешить любые внешние потребители роли до остановки, проверить активные jobs и scheduled maintenance.
  2. Создать зашифрованный recovery bundle из текущей DB schema/config/env/role metadata и restore-tested пары ciphertext+old key. Обёртка использует независимый новый recovery key, сохранённый отдельно mode0600; она не полагается на засвеченный AES key. Проверить восстановления на изолированной VPS БД без real tool invocations. Новый dump/schema data не печатать и не скачивать на Mac.
  3. Подготовить новые private секреты и env-кандидат. Env отличается только AES key и password component runtime DSN; tokens/header values, URLs, flags, Authentik configuration и остальной файл сохранены. Проверить renderer без вывода effective env и корректность quoted SCRAM/DSN. Journal подготовлен до commit.
  4. Остановить только gateway и дождаться завершения операций; не отменять dispatched writes с retry. Зафиксировать финальный revision и sealed backup после quiescence. Завершить оставшиеся сессии только роли mcp_gateway_runtime через существующее privileged local соединение; не чужие backend sessions. Повторно проверить отсутствие writer/jobs.
  5. Перешифровать все upstream/client rows с проверкой и CAS, сменить пароль роли выбранным протестированным механизмом. До env replacement проверка новой DB-аутентификации и полного decrypt под новым key; отказ old key и old password проверяется без логирования значений. При неопределённом commit — inspect state, не повторять mutation вслепую.
  6. Атомарно установить новый env-кандидат0600; final CI image overlay и существующий Compose helper. Пересоздать только gateway, без pull latest/dependencies restart. Проверить Config/image/revision и absence secret outputs. После приёмки синхронизировать только нужные private config-копии, если они существовали; новые секреты не экспортировать в canonical source tree.
  7. Записать зашифрованный post-rotation backup и bounded receipt. Оставшиеся gateway historical copies обработать согласно разделу6. При ошибке не переходить дальше и не возвращать засвеченные секреты автоматически.

6. Резервные копии и восстановление

Инвентаризировать gateway-owned исторические env/Compose snapshots, ciphertext dumps, temporary scripts и копии в backup/sync хранилищах. Имена/содержимое приватны; evidence содержит только counts/status. Смена действующего ключа не защищает исторические ciphertext, если старый ключ известен.

Перед удалением любой прежней рабочей копии сохранить её в независимо зашифрованном recovery archive, проверить restore и предоставить перечень на отдельное подтверждение очистки. Старую env не возвращать в эксплуатацию. Старые снимки можно восстановить в изолированную БД, немедленно перешифровать новым действующим key и оставить новый DB password. Восстановление live делается только после подтверждения, что gateway остановлен и нет новых пользовательских изменений после выбранного snapshot.

До SQL commit: транзакционный rollback и старый env остаются согласованы; сервис не поднимать, пока решение не принято. После commit, но до rename: довести env вперёд из staged новых секретов. При runtime regression: откатить только image к исходному binary (ciphertext format сохранён), оставив новые key/password. Restore ciphertext всегда парный с нужным ключом и тестом decrypt; automatic DB restore запрещён. При неопределённом состоянии использовать sealed journal и проверку обеих key generations в памяти.

Backup содержимое не теряется; окончательное удаление незашифрованных копий и обращение с внешними backup/sync destinations — отдельный завершающий шаг с конкретным перечнем. Ротация не позволяет отозвать уже записанное в журнале чата значение.

8. Согласование и решения до переключения

Редакция1 согласована пользователем для локальной реализации и synthetic репетиции; этот этап выполнен. Перед production покажу проверенный diff, CI-ready пакет, точный порядок транзакций, измеренную длительность окна, recovery evidence и перечень затрагиваемых private файлов. Commit/push новой утилиты и production переключение получат отдельное явное разрешение; прошлое разрешение относилось к connector-batch релизу.

Обязательные решения перед production: доказать выбранный SCRAM/no-leak механизм на PG17; зафиксировать atomic/split commit ordering по репетиции; завершить inventory внешних потребителей/backups; определить место independent recovery material с owner-only доступом и проверкой восстановления. Эти вопросы блокируют production, но не локальную разработку. Внешние backup deletions и глобальные настройки logging не разрешаются согласованием локального этапа.

Planning gate: AGENTS.md требует «Stop before implementation until the user approves»; html-implementation-plan/SKILL.md требует «Present the file and the concrete scope for approval before implementation». Этот gate пройден явным согласованием редакции1. Действующий production gateway продолжает работать с прежними секретами; production-этап отдельно не запускался.

Фактический результат локального этапа

Выполнено inline без subagents, commit/push, SSH/VPS действий и deployment. Новый explicit registry rotate-secret-key и store rotation охватывают обе encrypted tables; exact document сохранён, revision+1, fresh nonces/AAD, strict full validation/CAS. PostgreSQL17.11 репетиция доказала атомарный commit и rollback AES ciphertext + role password в одной транзакции. Вместо смены пароля из runtime-соединения выбран privileged maintenance path: transaction-local sensitive logging protection и отказ при обнаруженном pgaudit; runtime не получает новых прав.

Orchestrator prepare/apply: private files, отдельный recovery key, sealed dump/env/old-key archive, persisted phase journal, new physical runtime login, fsync/rename env. Готовность backup проверена envelope round trip и восстановлением pg_dump в отдельную БД; восстановленный snapshot проверен и перешифрован вперёд. Реальный процесс принудительно завершён после DB commit до journal update; повторный apply обнаружил завершённый commit без повторной mutation. Проверены rollback строки/password, stale/concurrent CAS, corrupt late row, rename/fsync failures, interruption после env replace, staged-file drift и повторный completed apply.
